| Record type | Field | CloudKit type | Use |
| --- | --- | --- | --- |
| `ReadingDataV1` | `sourceKey` | String | Hashed source identity, checked alongside the record identity. |
| `ReadingDataV1` | `readingData` | Encrypted Bytes | Encoded reading identity and version, including a value or deletion tombstone. |
| `StandaloneBookV1` | `metadata` | Encrypted Bytes | Encoded standalone book identity, edition and revision. |
| `StandaloneBookV1` | `tombstone` | Encrypted Bytes | Encoded deletion identity and revision. |
| `StandaloneBookV1` | `bookFile` | Asset | Original managed standalone book file. |

The book codec writes either `metadata` and `bookFile`, or `tombstone`; it clears the other fields. Both variants must therefore exist in the schema. The reading codec writes an encrypted tombstone within `readingData`, rather than physically deleting a CloudKit record. The app uses private databases, source-specific custom zones, record-ID lookups and zone-change enumeration; it does not rely on field queries or indexes for these flows. `bookFile` is a CloudKit asset, not an `encryptedValues` field. Apple documents separate asset encryption and encrypted-field behavior in [Encrypting User Data](https://developer.apple.com/documentation/cloudkit/encrypting_user_data).

## Before a production TestFlight test

1. With appropriate developer access, inspect and export the **existing** development and production schemas for the intended container. Keep management tokens out of chat, source control and logs. Do not reset an environment or import this inventory as a replacement schema.
2. Compare the existing record types, field names, types, encryption settings, indexes and permissions with the exact tested candidate. Check both live-book and deletion variants. Review all existing schema changes, not only LibraVia's expected fields.
3. Exercise schema creation and the candidate with synthetic data in an appropriate development environment if needed. Verify the resulting schema and aggregate privacy report. Apple notes that encrypted fields must be new fields and cannot be indexed; a pre-existing incompatible unencrypted field requires a migration design rather than conversion in place.
4. Prepare the exact schema diff for owner review. Production schema promotion is a separate, durable action and requires the owner's explicit authorization at the promotion checkpoint. Apple documents the production schema's additive-only constraints and the dashboard deployment process in [Deploying an iCloud Container's Schema](https://developer.apple.com/documentation/cloudkit/deploying-an-icloud-container-s-schema) and [Designing and Creating a CloudKit Database](https://developer.apple.com/documentation/cloudkit/designing-and-creating-a-cloudkit-database).
5. After authorized deployment, verify the production schema and the TestFlight build's container and environment. Then run the synthetic-data device journey in [PRIVATE_RECOVERY_VALIDATION.md](PRIVATE_RECOVERY_VALIDATION.md). A development signature, schema inventory or successful deployment is not evidence of a live recovery pass.
