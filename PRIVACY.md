# LibraVia privacy

LibraVia connects to the Jellyfin HTTPS server you choose. It has no publisher-operated account, advertising, analytics, or telemetry service integrated in app code. Reading still involves network requests to your server. That server's operator and Apple's system/TestFlight services have their own policies and may retain activity or diagnostics.

## Data handling

When you choose a book folder, LibraVia stores a device-local security-scoped bookmark and a catalog of supported files in app storage. It reads the selected folder and makes a managed copy when you open a book; it does not edit, move, or delete the source files. Folder paths and bookmarks remain local to the device.

| Data | Purpose and retention |
| --- | --- |
| Password | Sent to your selected server for login. Cleared from the login field when submitted; not persisted by app code. |
| Access token, server/account identifiers | Stored in device-local Keychain for session restoration; removed by local sign-out cleanup. |
| Catalog queries, book identifiers, reading progress | Sent to your selected server for browsing, downloading, and progress synchronization. |
| Covers, author/profile images | Retrieved from your selected server and held in session memory; no public image service is used. |
| Downloaded and extracted books | Automatically opened copies use an account-scoped 1 GB cache. Explicit offline saves and imports use separate local application support storage and are not removed by cache eviction. |
| Offline download queue | Account-scoped local journal of book metadata and download state; interrupted items can be retried. Sign-out removes the account's local journal. |
| Reading positions, titles, bookmarks, annotations | Stored in app support files scoped by normalized server endpoint, server ID, and user ID, or the separate On My Device library. Normalized Jellyfin progress is sent to Jellyfin. If private recovery is set up and run, precise positions, bookmarks, highlights and notes can also be sent to the private iCloud database for that source and account. |
| Private recovery book files and records | When standalone recovery is set up and run, managed standalone book copies, book metadata and reading data can be sent to the user's private iCloud database. Jellyfin recovery sends reading data, not Jellyfin book files. Recovery uses local journals, staged assets, account/source identifiers, edition fingerprints and deletion records to reconcile changes. Apple operates iCloud under its own policies. |
| Preferences, library selection, pseudonymous installation identifiers | Local preferences. The session identifier sent to Jellyfin is generated by the app rather than a hardware identifier. |

When a saved place belongs to a changed or unverified edition, LibraVia asks for review before opening at that place. Continuing preserves the earlier place as a bookmark before replacing the current position; cancelling keeps the position, and progress reporting stays on hold until review. These local backups remain part of reading data.

Reading-state files remain eligible for device backup. Preferences and server-specific pseudonymous identifiers can survive sign-out. Earlier endpoint-unaware namespaces are not migrated into the new account scope.

Sign-out attempts to remove credentials, account-specific cached and saved books, the download queue, and that account's active reading state. Reading state with pending iCloud recovery changes is retained locally rather than removed. Journals and safety backups from earlier recovery-account switches or migrations can also remain on the device; sign-out does not delete iCloud recovery records. Imported books and their reading data remain in the separate On My Device library. Removing a device copy does not delete a server book. Local removal cannot erase server history or existing device backups. Failed or offline server-token revocation does not establish that the server has invalidated the token; sessions can also be revoked through the server administrator.

Exporting reading data writes a user-selected Markdown or JSON file containing that book's bookmarks and local annotations. The exported file is controlled by the destination you choose and is not synchronized by LibraVia.

The current development candidate offers experimental private iCloud recovery for managed standalone books and reading data, and a separate reader action for Jellyfin-linked reading data. Each has optional foreground automatic retries after setup. A selected folder is not uploaded as a folder: managed copies of books opened or imported from it can be included in standalone recovery. The original folder and files remain user-owned. The Production CloudKit schema has been deployed and matched to the reviewed private recovery schema. Live behavior, account transitions and the handling of assets in the distribution-signed app have not yet been verified. Do not rely on iCloud restoration until the implementation and two-device tests are complete.

## Connection and document safeguards

Server fields start blank. HTTPS is required, including for reverse-proxy base paths. Embedded URL credentials, query strings, and fragments are rejected. The app uses Apple's certificate validation and refuses authenticated redirects. API networking uses ephemeral sessions with cookie, credential, and response caching disabled.

Ordinary SDK requests use an Authorization header. The official SDK's token-revocation endpoint places the token in its URL path; server and reverse-proxy operators should protect and redact access logs. No custom revocation protocol is substituted.

Keychain entries use unlocked, device-local protection and are not marked synchronizable. The app does not implement a biometric lock or guarantee password-memory zeroing. On macOS local book/state files are not separately encrypted by the app; OS account, disk, sandbox, and backup protections matter.

The current Mac development candidate uses the data-protection Keychain for saved sign-ins. It does not read, rewrite, migrate, or delete credentials left in the legacy file-based Keychain, including at sign-out. Users upgrading from a legacy build reconnect once to create a protected sign-in; existing book files and account-scoped reading data are retained. Sign-out removes the modern saved sign-in. Legacy entries remain under the user's control, and server-session revocation has the limits described above. A stable, properly signed app identity is required; an ad-hoc development build does not establish working credential access.

EPUB rendering uses a nonpersistent WebKit store and bundled local resources. Book scripts and unsolicited remote resources are blocked. Archive paths, sizes, counts, and extraction time are bounded; unsafe or unsupported books are rejected. These safeguards are not a certification against every hostile document or WebKit behavior.

## Privacy manifest and beta status

The privacy manifest explicitly declares an empty collected-data list, no tracking and no tracking domains. It declares own-app UserDefaults access (`CA92.1`), app-container file metadata (`C617.1`), and metadata for files and folders the user selects (`3B52.1`). These declarations do not replace App Store Connect privacy answers, the archive's aggregated SDK privacy report, or signed runtime verification. See [Apple's required-reason API guidance](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype).

The project is an MVP for internal testing. Final signed-app data handling, cleanup/cancellation, archive privacy, and cross-client synchronization still require verification as documented in VALIDATION.md. This repository document records app behavior; a distribution privacy-policy URL and publisher contact must be established before wider publication. Report sensitive concerns through SECURITY.md.
